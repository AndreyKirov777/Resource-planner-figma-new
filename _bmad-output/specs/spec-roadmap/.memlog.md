- (direction) User reopened the concept on 2026-08-21: "WBS is not a project plan; mapping it directly onto a Gantt is probably wrong." Agreed. The WBS leaf is the unit of estimation, not of time; deliverable hierarchy is not time hierarchy; level-of-effort nodes have no start/end; dependencies between deliverables are mostly false; a planner does not know the start week of sixty packages.
- (direction) User's proposal, adopted: keep the WBS exactly as it is; add planning as a SEPARATE high-level Gantt — a project roadmap, not a task schedule.
- (decision) SUPERSEDES spec-wbs-schedule. No WbsSchedule, no WbsDependency, no Schedule mode inside the WBS tab. The earlier "one tree, two modes" resolution is withdrawn: the common key for reconciliation is now the link, not WbsItem.id-as-task.
- (decision) Three artifacts, three jobs: WBS = what (unchanged), Roadmap = when (new), Plan = who (unchanged). Three reconciliations: what↔who (WBS-3, shipped), what↔when (coverage, new), when↔who (demand vs supply per period, new — the point of the feature).
- (decision) Roadmap is flat: RoadmapLane → RoadmapItem (bar | milestone). No nesting, stated as a constraint, not a deferral — depth is what turns a roadmap back into a schedule.
- (decision) Link model is N:1 with tree inheritance: RoadmapLink(wbsItemId unique → roadmapItemId) in its own table so WbsItem stays untouched; a linked node carries its subtree; nearest linked ancestor wins; a deeper link carves its subtree out. Modelled on effectivePhases in wbsTree.ts. Rejected alternatives: roadmap as a projection of WBS top levels (deliverable hierarchy ≠ streams/releases; items span phases; user wants decoupling), link via phase (too coarse — that is today), N:M with shares (double counting or unmaintainable profiles).
- (decision) Milestones carry no scope; they mark the end boundary of startPeriod with periodCount 0.
- (decision) Unplaced effort is NOT zero: it contributes a baseline demand spread over its effective phase, so the by-period picture is complete before any linking and agrees with WBS-3 by-phase by construction. Resolves the old open question. Effort with no item and no phase is "unplaceable" — excluded from periods, counted in the total.
- (decision) Invariant: Σ per-period demand + unplaceable hours == WBS-3 projectTotal. The by-period view redistributes the existing total, never produces a different one.
- (decision) Engine contract is "demand distribution per item" (Map<period, Map<role, hours>>); a bar is one producer, the phase baseline another; a future profile editor is a third and changes nothing downstream.
- (decision) Dependencies, auto-scheduling and critical path are OUT. The user's earlier override making them mandatory applied to the task-level model; at roadmap altitude the user accepted cutting them. A display-only "starts after X" hint is listed under Slice C on request only.
- (decision) Bootstrap from WBS (CAP-12) ships in Slice A: depth-0 nodes → lanes, depth-1 nodes → items linked to subtrees and windowed by effective phase, previewed before a transactional bulk write. Answers the "double entry" objection.
- (decision) Roadmap is a new top-level tab after WBS (the old "no new tab" rule was about a mode over the same rows and no longer applies). The WBS tab gains one optional, hidden-by-default Roadmap column and nothing else.
- (decision) SVAR stays the chosen library, with lanes as summary rows (bar suppressed) and items as tasks; links and resources features unused. Gate 0 gains an honest comparison with a hand-rolled CSS-grid timeline, since a flat roadmap of ~20 rows may not need a Gantt engine.
- (decision) Slices: Gate 0 spike → A "a roadmap with scope" (tab, lanes/items, timeline, drag, editor with scope picker, WBS column, effort on bars, coverage cards, bootstrap) → B "capacity" (demand engine, stripes, load strip, by-period matrix, feasible duration, draft plan) → C on request.
- (question) Weekly↔monthly conversion and phase reorder/split/delete remap rules for items; export/import schemaVersion 4; ResourceLoad in MIT; cross-lane drag event shape; compact lanes.
- (event) Spec rebuilt 2026-08-21: SPEC.md + data-model.md + ux-reference.md + svar-integration.md + delivery.md. Paused for user review before any implementation.
- (event) Interactive UI mockup built and published 2026-08-21: https://claude.ai/code/artifact/c480e057-abe0-4618-9e74-91791e66e8bf — all six screens (roadmap, editor panel with scope picker, reconciliation coverage cards + by-period matrix, WBS Roadmap column, empty state, bootstrap preview) on one demo project (16 weekly periods, 4 phases, 4 lanes, 12 items, 5 160 h WBS vs 4 800 h plan). Figures are computed in-page by the data-model formulas and asserted in node: sum of per-period demand equals the WBS total, linked-subtree effort equals itemEffort, stripes cover only over-demand periods.
- (question) Mockup surfaced two contradictions with the contract, now recorded in SPEC Open Questions: feasiblePeriods ignores contention between items (says "could be shorter" while the same periods are overloaded), and bootstrap leaves depth-0 leaves unplaced so CAP-12's "zero unplaced hours" criterion cannot hold. Also raised: level-of-effort work may need kind "spread", and the load strip may want an all-roles default.
- (event) Code-level SVAR audit 2026-08-21, first-hand: tarballs unpacked, original TS/JSX recovered from shipped source maps, packages installed and Vite-built twice for a measured bundle delta, behaviour reproduced in node, issue tracker checked via GitHub API. Findings in scratchpad audit-bars.md / audit-scale.md / audit-footprint.md / findings-mine.md.
- (recommendation) Build the roadmap chart on CUSTOM components, not SVAR. Decisive asymmetry: SVAR has NO cross-lane bar drag (clientY never read in Bars.jsx; reparenting is a grid-row gesture via move-task) so a custom pointer layer is required either way, which removes the main reason to adopt it. Everything else it would give arrives with a suppression cost: summary bar hidden by CSS only, link+progress affordances always rendered, resize handles with no DOM (computed outer 20% of bar), readonly a single boolean, no per-task CSS class (only a task.type hack), expandScale silently overriding our cellWidth, uneven phase bands only via a module-global registerScaleUnit, and a live crash on a childless open lane (issues #28/#31, reproduced). The demand engine, load strip, editor panel and reconciliation are ours regardless.
- (note) Measured, not estimated: SVAR costs +90 KB gzip (+84.9 JS, +5.2 CSS) and 40 packages; licences are clean (34/34 MIT, no keys, no telemetry) but Willow/Material fetch an icon font from cdn.svar.dev unless fonts={false}. Custom drag+resize+cross-lane with snap-on-release, ghost, clamps and Undo came to 146 LOC with 16 passing assertions; rows+bars 65 LOC, header 12 LOC, chart CSS 168 LOC.
- (note) The app ALREADY renders uneven phase bands over period columns: ResourcePlan.tsx:407-437 uses glide-data-grid column group + getGroupDetails overriding bgHeader with PHASE_COLORS. The one thing SVAR needs a global registry hack for is solved in this codebase.
- (correction) Issue numbers in delivery.md and svar-integration.md are WRONG. #14 ("Broken in Vite, CRA, NextJS, Parcel") and #20 ("Links can not be deleted") are long closed; #10 is a feature request, not a scroll freeze. Live and relevant: #28 and #31 (childless-node crash), #30 (cellWidth scaling). If SVAR is dropped, both companions are superseded rather than corrected.

- (direction) User accepted the audit's recommendation on 2026-08-21 and asked for the spec to be rewritten for custom components.
- (decision) SUPERSEDES the SVAR library choice. No Gantt or timeline dependency is added for this feature; the roadmap chart is built in-house. svar-integration.md carries a SUPERSEDED banner (including the correction that its issue numbers #10/#14/#20 are wrong) and is kept for the audit trail only. New companion timeline-component.md is the chart contract.
- (decision) Pixel geometry is a pure module src/utils/roadmapGeometry.ts (periodX, periodAtX, barRect, milestoneX, phaseBands, rowAt, snapDrag, stripeSegments), unit-tested without React or DOM, following the wbsGrid.ts precedent. No component computes coordinates inline. data-model.md stops at periods; roadmapGeometry turns periods into coordinates. That seam is what survives a change of renderer.
- (decision) snapDrag is the whole interaction rule in one testable function, with three modes (move, resizeStart, resizeEnd): move never changes duration; resizeEnd changes duration only; resizeStart compensates so the finish period does not move; minimum 1 period; clamped to [1, np]; a milestone always returns periodCount 0.
- (decision) The bar follows the pointer pixel for pixel and snaps only on RELEASE, with a dashed ghost showing the landing rect. Snapping mid-gesture makes short drags fight the cursor. Restated in timeline-component.md because the implementation is where this gets lost.
- (decision) NEW HARD REQUIREMENT: every drag gesture has a keyboard equivalent routed through the same snapDrag and commit path (arrows move, shift+arrows resize the finish, alt+arrows resize the start, ctrl+up/down change lane, Esc cancels). A bar placeable only by dragging is not shippable, and the keyboard path is also what component tests drive, so no pointer harness is needed. Folded into CAP-4's success criteria.
- (decision) Layout: three column grids (header, rows, load strip) aligned from one periodWidth and one period count, with exactly one horizontal scroller (the chart) driving the strip's scrollLeft one-way. Phase tint is one absolutely-positioned layer of period-wide columns behind the rows.
- (decision) No virtualization, no canvas, no free-pixel zoom. A roadmap is a few hundred DOM elements; full re-render on change is correct. Revisit only past 150 rows or 200 periods, and then only by windowing rows, which is local because geometry is pure. Added to non-goals.
- (decision) Theming uses app tokens from styles/globals.css directly. SPEC's "header 36" corrected to 44 to match ux-reference. Precedent to read first: ResourcePlan.tsx:407-437 already renders uneven phase bands over period columns via glide-data-grid column group + getGroupDetails.
- (decision) Gate 0 removed entirely. The mockup is the spike. delivery.md now names what it settled (grid alignment, 146-LOC pointer layer with 16 passing snapDrag assertions, uneven phase bands in both themes, the demand invariant, the coverage categories) and what it did NOT (persistence, .strict() schemas, keyboard parity, the scope picker's write path, bootstrap on real WBS shapes, mode conversion and phase edits, React reconciliation — the mockup re-renders by innerHTML).
