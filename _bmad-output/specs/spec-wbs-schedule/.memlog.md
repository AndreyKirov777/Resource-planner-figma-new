topic: WBS Schedule (Gantt) mode: a second view of the WBS tree on a period timeline, built on SVAR React Gantt (MIT), whose purpose is reconciling WBS effort x schedule duration against Resource Plan capacity
updated: 2026-08-21T15:18
---

- (direction) Scope comes from the in-conversation research plus UX plan revision 3: a free-only React Gantt comparison, then a UX plan for a Schedule mode inside the WBS tab. Development happens on branch feat/wbs-schedule-gantt, cut from feat/ai-plan-generation (main is 120 commits behind).
- (decision) Library: SVAR React Gantt (@svar-ui/react-gantt 2.7.x, MIT). Chosen over DHTMLX Community v10, gantt-task-react forks, XGantt, VTable-Gantt and Syncfusion for being native React, allowing React components as grid cells and column editors, ~90 kB gz, CSS-variable theming. Not wx-react-gantt (deprecated, GPLv3).
- (decision) Gantt is a PLANNING instrument, not project management. No progress, baselines, actuals or statuses - absent, not hidden. User confirmed this framing explicitly.
- (decision) Core value is not the bars but three-layer reconciliation: effort (WbsEstimate hours) divided by duration (schedule periods) gives demand per (role, period) in FTE; Resource Plan Allocation gives supply; their per-period difference is what the mode exists to show.
- (decision) One WBS tree, not a separate schedule entity. User raised the PMBOK concern that WBS (effort) and Gantt (duration, dependencies) are different artifacts; resolved by separating at the TABLE and MODE level rather than the entity level - a second tree would drift from the WBS, and reconciliation needs a common key, which is WbsItem.id.
- (decision) Schedule lives in a new optional 1:1 table WbsSchedule(wbsItemId unique, startPeriod, periodCount, kind). WbsItem and WbsEstimate are untouched, so the WBS stays a pure effort estimate and existing export/import/reconciliation contracts do not move.
- (decision) Schedule is stored in PERIODS (integers in the project planningMode unit), never ISO dates. Rationale: aligns with Allocation.periodNumber, with the weekly/monthly conversion in modeConversion.ts, and with phases; makes per-period reconciliation direct instead of a date-to-period translation.
- (decision) Modes are named by the job - Estimate and Schedule - not by the widget (Table and Gantt), so the split between estimating effort and laying it on time is visible in the UI itself.
- (decision) Each mode edits only its own layer; the other layer is shown read-only - hours read-only in Schedule, duration read-only in Estimate.
- (note) batch 1 boundary
- (capability) CAP-1 Mode switch: an Estimate/Schedule ToggleGroup in the WBS tab header preserves selection, collapsed nodes and scroll position across switches; persisted per project in localStorage like loadHiddenColumns.
- (capability) CAP-2 Schedule storage: a WBS item can carry startPeriod plus periodCount, or carry none - an unscheduled item is a valid, normal state and renders as a derived range spanning its phase.
- (capability) CAP-3 Period timeline: a two-level scale of phase bands (PHASE_COLORS, with WBS hour totals) over period columns labelled by ordinal and calendar date derived from Project.startDate; stepped zoom by planning unit plus Fit.
- (capability) CAP-4 Direct-manipulation scheduling: drag and resize snap to period boundaries; dragging a bar into another phase band reassigns phaseName and offers a single-operation undo via toast.
- (capability) CAP-5 Bar semantics: leaf bars carry hours and FTE, parents render as summary bars spanning their children, zero-hour leaves may be milestones, unscheduled items render as derived ghost bars, and periods whose demand exceeds Resource Plan supply carry a warning stripe.
- (capability) CAP-6 Demand engine: a pure module computes demand per (role, period) from estimates and schedule, supply from allocations, their variance, and the feasible duration of a task at current staffing.
- (capability) CAP-7 Load panel: a per-period demand-versus-supply strip under the timeline, selectable by role or discipline, in the same column grid as the timeline.
- (capability) CAP-8 Reconciliation by period: the existing ReconciliationPanel gains a by-period section beside by-discipline and by-phase, plus an out-of-phase category for items whose periods fall outside their phase.
- (capability) CAP-9 Task editor: a non-modal side panel that compresses the timeline rather than covering it, with fields from the existing model, the existing RolesEditor for roles, computed demand-versus-supply and feasible duration, and autosave on blur.
- (capability) CAP-10 Draft Resource Plan from schedule: per-period demand can be turned into draft plan rows and allocations through the existing GeneratePlanSheet draft-preview-apply flow.
- (capability) CAP-11 Structure parity: row context menu and structure hotkeys (add sibling and child, indent, outdent, delete) behave identically in both modes.
- (note) batch 2 boundary
- (constraint) Hours are the source of truth. SVAR stores an assignment share as a percentage (units); the app stores absolute hours in WbsEstimate. Any units value handed to SVAR is derived for display only and never written back as truth.
- (constraint) Every write goes through src/services/api.ts; no component calls fetch. New request fields require the matching .strict() Zod schema in server-validation.ts, or the write returns 400.
- (constraint) Schedule and demand logic are pure functions in src/utils/, unit-tested without React or DOM, following the existing wbsGrid.ts and wbs.ts pattern.
- (constraint) Reuse rather than re-derive: getPhaseForPeriod and phaseStartOffset (phases.ts), hoursPerPeriod (calculations.ts), resolveDiscipline (wbs.ts), availableRoles and deriveDiscipline (RolesEditor), createEstimateCommitter (wbsGrid.ts), and the draft-preview-apply flow in GeneratePlanSheet.
- (constraint) Free edition only: @svar-ui/react-gantt under MIT. No PRO packages, no private registry, no license keys.
- (constraint) The Estimate mode keeps its current glide-data-grid implementation unchanged; Schedule mode does not attempt to reproduce the full glide table in the SVAR left grid.
- (constraint) Visual parity with the app: row height 34, header 36, Inter, tokens from styles/globals.css, PHASE_COLORS for phase bands, grid accent 8f4f8f, theme following next-themes via Willow and WillowDark.
- (constraint) npm run typecheck must pass before any slice is called done - the build does not type-check and CI runs both.
- (constraint) Work lands on branch feat/wbs-schedule-gantt; prisma/dev.db is untracked and must not be committed or reverted.
- (decision) Resource picking uses the existing RolesEditor, not SVARs built-in Resources tab. Verified that SVAR assignments ARE available in the MIT build, but SVAR picks a resource plus a percentage while this app needs a role plus hours with the discipline derived from the rate card; a second picker with different semantics would confuse. SVARs avatar-group column may still be adopted for display.
- (decision) Dependencies between tasks are deferred, not merely unimplemented: without PRO auto-scheduling the links would be drawn but inert, which is worse than their absence. They return only when a real shift-on-change rule is wanted.
- (note) batch 3 boundary
- (note) Non-goal: task dependencies, auto-scheduling, critical path, slack.
- (note) Non-goal: progress, baselines, actuals, task status - the mode plans, it does not track.
- (note) Non-goal: a capacity view with people or roles as rows and assignments as bars; that is a separate later feature and, if built, on a resource-timeline library rather than SVAR.
- (note) Non-goal: multiple activities per WBS item, or several what-if schedule scenarios per project; WbsSchedule stays 1:1 until a real need appears.
- (note) Non-goal: named individuals as resources - the Resource List holds roles and rates, not people.
- (note) Non-goal: changing Estimate mode behaviour, the reconciliation math already shipped in WBS-3, or the glide-data-grid tables.
- (assumption) Demand is spread evenly across a task's periods. A ramp or front-loaded profile is a later refinement and does not change the data model.
- (assumption) A period's capacity in hours is hoursPerPeriod(planningMode, daysInFTE); FTE figures shown to the user are demand hours divided by that value.
- (assumption) Project.startDate anchors period 1; calendar dates on the scale are derived from it and never stored per item, so moving the start shifts the whole scale without touching any schedule row.
- (question) Does the ResourceLoad component actually work in the MIT build? Its code looks complete and the pricing page lists the load chart as PRO. If it works, CAP-7 needs no custom chart; if not, build it on recharts. Decide in the spike.
- (question) What happens to WbsSchedule rows when the planning mode is converted weekly<->monthly? modeConversion.ts remaps allocations; schedule rows need an equivalent rule, and the conversion is already documented as lossy.
- (question) What happens to WbsSchedule rows when phases are reordered, split or deleted in Resource Plan? phases.ts has remapPeriodNumber for allocations; schedule rows likely need the same remap.
- (question) Should the JSON project export/import carry WbsSchedule and Project.startDate? WBS-4 shipped export/import for WbsItem and WbsEstimate; leaving schedule out would silently drop it on round-trip.
- (question) Should an unscheduled item contribute derived demand (spread across its phase) to the load panel and by-period reconciliation, or count as zero until explicitly scheduled? The mockup shows a derived ghost bar; whether it also feeds demand is undecided.
